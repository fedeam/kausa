# Thirty-two namespaces

How much memory kausa uses, and how long it takes to be ready, when it watches 32 namespaces on
their own: 64 watches and 64 connections to the API server, against the chart's memory limit of
128 MiB. Measured on 2026-10-28 as the condition of shipping the namespaced mode with a cap of 32
namespaces ([0013. Offer a namespaced install mode: one watch pair and one Role per listed
namespace, and nothing cluster-wide](../adr/0013-namespaced-install-mode.md)), which would have
lowered the cap to 16 or 8 if kausa had not stayed well under the limit.

Once per scope, in a kind cluster on the maintainer's machine: a first data point, not a benchmark.

## Result

| | `rbac.scope=cluster` (2 watches) | `rbac.scope=namespaced`, 32 namespaces (64 watches) |
|---|---|---|
| Ready (`/readyz` 200) after the `started` line | 0.55 s | 0.48 s |
| Ready after `helm install` returned (scheduling and container start included) | 5.9 s | 5.2 s |
| Memory when ready (working set) | 4.5 MiB | 10.5 MiB |
| Memory in steady state, 15 s to 3 min after ready (working set) | 4.9 to 5.5 MiB | 10.1 to 14.2 MiB |
| Highest memory since the container started (`memory.peak`) | 14.8 MiB | 22.7 MiB |
| Restarts, watch errors | 0, 0 | 0, 0 |
| Incidents logged (and requests, in dry-run) | 4 | 4 |

- **The cap of 32 stays.** With 64 watches kausa used at most 23 MiB, under a fifth of the 128 MiB
  limit, and about 13 MiB once settled. The mode ships with `--namespace` repeatable up to 32
  times and `rbac.namespaces` up to 32 names; nothing was lowered.
- **Each watch pair costs little.** The 62 extra watches cost about 8 MiB in steady state, about
  130 KiB each. The records are the same in both runs (the same 964 Pods), so it is the cost of a
  connection and a watch stream (hypothesis: their buffers; not profiled).
- **Readiness does not wait for the namespaces one by one.** The 64 watches are polled together,
  so they list concurrently, and kausa was ready half a second after it started, as fast as with two watches. The time from
  `helm install` is mostly the Pod being scheduled and started.
- **The incidents are the same.** The four seeded failures (a crash loop and a failed Job in each
  of two namespaces) gave the same four incidents and dry-run requests in both scopes.

## Setup

- kind with Kubernetes v1.36.4 (the node image pinned in `.github/workflows/e2e.yml`), one node.
- The objects of [Thousands of Pods](2026-10-28-thousands-of-pods.md), written by
  [`tests/bench/thousands-of-pods.py`](../../tests/bench/thousands-of-pods.py) with
  `32 10 3`: 32 namespaces (`scale-00` to `scale-31`), each with 10 Deployments of 3 replicas bound
  to a fake node, 960 Pods in all that never run. Then `tests/e2e/failures.yaml` in `scale-00` and
  `scale-31`: a Deployment in a crash loop and a failed Job each, with kausa's own image.
- kausa from the branch of the namespaced mode (the merge of the code and chart tracks with
  `main`), the `runtime` image, installed with the chart in the repository: `dryRun=true`,
  `settleSeconds=10`, the default resources (limit 128 MiB), and either `rbac.scope=cluster` or
  `rbac.scope=namespaced` with the 32 namespaces (32 Roles, 32 RoleBindings, 32 `--namespace`
  arguments, nothing cluster-scoped). Each scope in a fresh cluster.
- Memory: `crictl stats` inside the kind node, which reads the container's cgroup (it works with
  the distroless image, which has no shell), right after ready and every 15 seconds for three
  minutes; then the cgroup's `memory.peak`. Ready: `/readyz` polled every 0.2 seconds through
  the API server's Pod proxy, compared with the `ts` of kausa's `started` line.

## Limits

- One machine and a local API server. The host's clock and the kind node's (inside Docker
  Desktop's VM) were compared without correction, and each poll took a fraction of a second, so the
  times to ready are good to about half a second.
- The Pods never run, so the namespaces produce no Warning events beyond the seeded failures: the
  event watches are nearly idle. Many Warning events, or a much larger cluster, add records, as
  [Thousands of Pods](2026-10-28-thousands-of-pods.md) measured in cluster scope (31 MiB with
  10,000 Pods).
- Three minutes is a steady state for watching, not a long run: the explanation path ran in
  dry-run only, with no model call.
