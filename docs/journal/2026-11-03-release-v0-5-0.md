## A key error inside a `400` (#72)

After the release, [#72](https://github.com/fedeam/kausa/issues/72): Google's Gemini API answers a
wrong key with a `400`, which [0020](../adr/0020-check-the-endpoint.md) classifies as `rejected`.

- **The bodies, captured with fake keys** (no real key used), from the OpenAI-compatible endpoint:
  a key that is not of the new format (`not-a-real-key`, and `AIza…` keys of 38 and 39
  characters) gets `Please pass a valid API key`, one of the new format (`AQ.…`) `Invalid Auth
  key.`, and no `Authorization` header `Missing or invalid
  Authorization header.`, each with `error.status` `INVALID_ARGUMENT`, a `code` of `400` and no
  `details`. A key sent as `x-goog-api-key` instead is not read there (the same `Missing or
  invalid Authorization header.`). A malformed request with a fake key gets the same status with
  a message that quotes the request and a `google.rpc.BadRequest` in `details`: the format is
  checked before the key.
- **The issue's hypothesis did not hold:** no `details[].reason` such as `API_KEY_INVALID`, and
  `INVALID_ARGUMENT` alone also means a malformed request. So the change compares the whole
  `error.message` too, byte for byte, with the three captured ones, on a `400` only
  (`KEY_ERRORS`, an Update to 0020).
- **Checked:** `kausa check-endpoint` against Gemini with a fake key and with none now ends with
  `cause: key`, `class: configuration` and the key's hint (before: `rejected` and the
  `--no-json-schema` hint). The unit tests use the captured bodies, the quoting one among them,
  and the fuzz target `endpoint_error` checks that only a listed pair makes a key error.

## Later the same day: self-observability

Request: v0.6's first theme, kausa's own observability: an alerting rules file checked and
unit-tested by a pinned `promtool` in CI, a reference page for the alerts, and the self-metrics
that were missing. No ADR: no permission, flag or request field changes, and nothing new is sent
to the model or the webhook.

- **Metrics** (`src/metrics.rs`, `src/run.rs`, `src/explain.rs`): `kausa_watch_relists_total` and
  `kausa_watch_restarts_total` per watch; the gauges `kausa_build_info`, `kausa_records`,
  `kausa_owner_cache_entries` and `kausa_dedup_cache_entries`; the first histogram,
  `kausa_model_call_duration_seconds` by outcome, whose `_count` equals `kausa_model_calls_total`
  because one helper counts and times each call; and the counters with a fixed set of label
  values start at `0` for each value in the modes that can count them. A test pins the whole
  exposition to `tests/golden/metrics.prom`, with a fixed version in `kausa_build_info` so that a
  release does not change it.
- **Rules and CI:** `deploy/prometheus/kausa-alerts.yaml` (eleven alerts in five groups) and its
  unit tests `tests/prometheus/kausa-alerts.test.yaml` (fourteen groups), copied unchanged from
  the verified drafts (SHA-256 checked). The `Dockerfile`'s `ci` target installs promtool from the
  Prometheus release archive, pinned by version and a SHA-256 per architecture, and runs
  `promtool check rules --lint=all --lint-fatal`, `promtool test rules` and `promtool check
  metrics` on the golden exposition; `AGENTS.md` lists the same three in the same order.
  `tests/e2e/run.sh` asserts the new series in the kind runs, and `tests/chart/render.sh` checks
  the files' shape with helm alone.
- **Docs:** [Alerts](../reference/alerts.md), one section per alert with its expression, what it
  means, when it does not fire and what to do; a test in `src/metrics.rs` ties the rules' metric
  names to the lists in the code and each alert to its section, its `runbook_url` and its
  expression. [Command line and log format](../reference/command-line.md#metrics) documents the
  new metrics; the pages that carried example alerts link Alerts instead; 0020 has an Update.

Checked on 2026-11-03, on the integrated branch:

- **The pin:** the latest Prometheus release that is not a pre-release is still v3.15.1 (v3.16.0
  is at release candidates), and the two checksums of its `sha256sums.txt` match the
  `Dockerfile`'s.
- **promtool 3.15.1**, from the official image pinned by digest, run in Docker with no network
  and the files read-only, then removed: `check rules` found 11 rules with no lint, `test rules`
  passed, and `check metrics` read the golden exposition with no message. The mutation script
  applied 61 single changes to the rules (each window and `for` moved by a minute either way,
  each count threshold by one step, each `> 0` raised to `> 1`, `time() - 3600` moved by 60
  seconds, the equality operands moved by one): all 61 made `promtool test rules` fail.
- **The Rust tests**, and seven single changes against the new test of the rules (a metric renamed
  in the rules or in the code, a section removed or added, a second label, a wrong anchor, a
  promql block that differs): each made it fail.
- **Not run locally:** `docker build --target ci .` and the kind test; the pull request's CI runs
  both, on amd64 and arm64 and in the three kind jobs.

Decisions, as the maintainer settled them: D1, the counters with fixed labels start at `0` per
value; D2, the rules in `deploy/prometheus/` and their tests in `tests/prometheus/`; D3,
`runbook_url` on `blob/main`; D4, `severity: warning` on all eleven; D5, promtool in the `ci`
target, about 100 MB more download and a layer of about 112 MB; D6, the rules file as a release
asset is left to theme 2; D7, the two leader alerts add up `by (namespace, job)`; D8,
`kausa_records` counts every Pod but only the Warning events and Deployments kausa keeps; D9,
`KausaLeaderFlapping` at `>= 7`, since six takeovers read more than 6 once `increase`
extrapolates. Not kept from the spec: that a call that times out lands in the bucket of its limit
(the time measured includes the wait up to the timeout, so it may fall just above the bound; not
measured).

Hypotheses still open: GitHub's anchors for the `### Kausa…` headings (lowercased names, as each
`runbook_url` assumes); the `namespace` and `job` labels a `PodMonitor` adds; the layout of the
Prometheus archive (`prometheus-<version>.linux-<arch>/promtool`) and that its static promtool
runs on the CI image (the first CI run settles both); the watch-error threshold outside the one
cluster measured; that a shorter scrape interval extrapolates less.

Follow-ups: theme 2, the rules file as a release asset (D6) and `runbook_url`s per tag; theme 3,
soak samples of `kausa_records`, the cache gauges and the call-duration histogram, which have no
alert until a threshold is measured.
