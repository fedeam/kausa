## A key error inside a `400` (#72)

After the release, [#72](https://github.com/fedeam/kausa/issues/72): Google's Gemini API answers a
wrong key with a `400`, which [0020](../adr/0020-check-the-endpoint.md) classifies as `rejected`.

- **The bodies, captured with fake keys** (no real key used), from the OpenAI-compatible endpoint:
  a key that is not of the new format (`not-a-real-key`, and `AIza…` keys of 38 and 39
  characters) gets `Please pass a valid API key`, one of the new format (`AQ.…`) `Invalid Auth
  key.`, and no `Authorization` header `Missing or invalid
  Authorization header.`, each with `error.status` `INVALID_ARGUMENT`, a `code` of `400` and no
  `details`. A key sent as `x-goog-api-key` instead is not read there (the same `Missing or
  invalid Authorization header.`). A malformed request with a fake key gets the same status with
  a message that quotes the request and a `google.rpc.BadRequest` in `details`: the format is
  checked before the key.
- **The issue's hypothesis did not hold:** no `details[].reason` such as `API_KEY_INVALID`, and
  `INVALID_ARGUMENT` alone also means a malformed request. So the change compares the whole
  `error.message` too, byte for byte, with the three captured ones, on a `400` only
  (`KEY_ERRORS`, an Update to 0020).
- **Checked:** `kausa check-endpoint` against Gemini with a fake key and with none now ends with
  `cause: key`, `class: configuration` and the key's hint (before: `rejected` and the
  `--no-json-schema` hint). The unit tests use the captured bodies, the quoting one among them,
  and the fuzz target `endpoint_error` checks that only a listed pair makes a key error.

## A Secret name past `R010`

The v0.6 measurement of explanation quality ran the known-cause corpus again, and its `no-volume`
request (`D007`) carried the name of the missing Secret in clear:
`MountVolume.SetUp failed for volume "credentials" : <redacted:value> "<name>" not found`.

- **Cause, reproduced in a unit test:** `R010` reads `"credentials" : secret` as a secret key and
  its value, and replaces the kind `secret` with `<redacted:value>`; `R003` then no longer sees
  `secret "<name>"`. Any volume named like a secret key (`credentials`, `api-token`, `password`,
  `auth`, `db_secret`) and any kind of `R003` (a ConfigMap too) did it, on the request and on the
  answer. Only the object's name was exposed, never a value.
- **Fix:** `R010` captures a quoted Kubernetes name after a bare value; when the value is a kind
  of `R003` alone, the match stays as it is and is not counted, and `R003` redacts the name. The
  quoted name can hold no key or separator, so it hides no other `R010` match (`token="a"
  "password=xyz"` still redacts both values). Tests for both passes and their counters.

## Later the same day: the OCI chart, Artifact Hub and SBOMs (0023)

The implementing change of [0023](../adr/0023-oci-chart-and-sbom.md): `cargo auditable` in the
`Dockerfile`'s build stage, Artifact Hub metadata and a README in the chart, and a `Release`
workflow that also pushes the chart to GHCR and attests a CycloneDX SBOM per image. Signing,
`actions/attest` and GHCR only run on a tag, so before v0.6.0 the commands were rehearsed locally,
against a throwaway registry (`registry:3`, pinned by digest, on a loopback port), with the
darwin-arm64 builds of the pinned versions: Helm v4.3.1 (checked against its `.sha256sum`), syft
v1.55.0 (its checksums file verified with `cosign verify-blob` and syft's release identity, then
the line) and oras v1.3.6 (its checksums file). The `linux_amd64` lines of syft and oras, which
`release.yml` pins, matched the pins and GitHub's asset digests, and `actions/attest` v4.2.2 is
still commit `1e69f48a…`. Nothing was pushed to GHCR, no tag was made and no registry was logged
in to.

### The rehearsal

- **The runtime image, once, arm64, with the classic builder** (`DOCKER_BUILDKIT=0`) and the
  `Dockerfile` cut from the build stage's `FROM` line on, as the Gitea job builds it: the
  cargo-auditable archive passed `sha256sum -c` (`/tmp/cargo-auditable.tar.xz: OK`), `cargo
  auditable build` finished in 1m 48s and the `.dep-v0` guard passed. The image is 10 MB, its user
  is `65532:65532` and `--version` prints `kausa 0.5.1`, the format `tests/cli.rs` checks. The
  amd64 guard is left to the pull request's image job. The image stays on the build machine as
  `127.0.0.1:5055/fedeam/kausa:0.5.1-arm64`.
- **The pushed image's manifest:** Docker Desktop here uses the `overlay2` store, not containerd's;
  the push wrote a single-platform `application/vnd.docker.distribution.manifest.v2+json` manifest,
  and `RepoDigests[0]` is the SHA-256 of the bytes that `docker buildx imagetools inspect --raw`
  returns for the tag (the same bytes as a plain `curl` of the manifest).
- **syft** scanned the pushed digest with `--platform linux/arm64`: CycloneDX 1.6, 467,988 bytes,
  1,115 components, of which 162 `pkg:cargo` (`kausa@0.5.1` and `kube@4.2.0` among them), 6
  `pkg:deb` (`base-files`, `ca-certificates`, `media-types`, `netbase`, `tzdata`,
  `tzdata-legacy`) and 946 files. kausa's purl is in `.components`; `.metadata.component` is the
  image. The `sbom` job's step, run as written (only its loop cut to arm64), passed its `jq -e`
  guard; the guard refused a copy relabelled `1.7` and a copy without the Debian packages. syft
  needs `SYFT_REGISTRY_INSECURE_USE_HTTP=true` for a plain-HTTP registry (local only), and `syft
  config --load` shows `check-for-app-update: false` under `SYFT_CHECK_FOR_APP_UPDATE=false`.
- **The chart with Helm 4.3.1:** `helm push` printed a `Digest:` equal to the SHA-256 of the tag's
  raw manifest; the manifest has the helm config media type, one
  `application/vnd.cncf.helm.chart.content.v1.tar+gzip` layer whose digest is the `.tgz`'s
  SHA-256, and no top-level `mediaType`; the same file pushed twice gave the same digest; the
  package lists `kausa/README.md` and no `artifacthub-repo.yml`. One difference from Helm 3.16.1:
  packaging an unchanged checkout twice gave the same `.tgz` bytes with 4.3.1 (its tar entries
  carry the files' times on disk), while 3.16.1 writes the time of packaging, so its two packages
  differ. The manifest still changes on repackaging, because `org.opencontainers.image.created` is
  the `.tgz` file's time. The workflow does not depend on either: it pushes the file it attaches
  and compares the layer with it.
- **Artifact Hub's metadata:** `oras push` of an `artifacthub-repo.yml` with the dummy
  `repositoryID` `00000000-0000-0000-0000-000000000000` to the `artifacthub.io` tag wrote a manifest
  with both Artifact Hub media types (an empty config, no `artifactType`). `helm show chart`
  without `--version` still resolved 0.5.1, with Helm 3.16.1 and 4.3.1.
- **The workflow's shell:** every `run:` block of `release.yml` passes `sh -n` and `bash -n`. The
  notes step, run as written with fake digests, a fake `CHANGELOG.md` section and a stub in place
  of `cosign`, left no placeholder, and the four `sh` blocks of the notes pass `sh -n`. "Check the
  version and the inputs", with `IMAGE` and the `grep -Eqx` pattern pointed at the local registry
  and the digest loop cut to arm64, passed with the real `RepoDigests` line and wrote the
  registry's digest; it refused a two-line file, two references without a trailing newline, the
  pushed chart's digest under the image's name, an empty file and a reference to another registry,
  and also an SBOM other than the one described and, with `gh` stubbed, a tag already released.
- **`--version` with a chart URL:** Helm 3.16.1 and 4.3.1 accept and ignore it (`helm template` of
  the v0.5.1 URL renders with `--version 0.5.1` and with `--version 0.4.0` alike), so it may stay
  in the URL examples but checks nothing there.
- **kind** (`kindest/node:v1.36.4`, its kubeconfig in a scratch file): a release installed with
  Helm 4.3.1 from the v0.5.1 chart URL (`rbac.scope=cluster`, `dryRun=true`) was upgraded from the
  local OCI chart with `--version 0.5.1 --reuse-values`; `helm get values` kept both values and

Hypotheses of the plan, as of 2026-11-03:

- Helm 4.3.1 behaves as 3.16.1 did (H4): checked for the digest per file, the layer and the raw
  manifest; not for repackaging, which no longer changes the `.tgz` bytes (above).
- `cargo auditable --version` works (H5b): does not hold. It passes the flag on to `cargo` (the

- syft reads `.dep-v0` and distroless's dpkg status, and kausa's purl is `pkg:cargo/kausa@<version>`

- `-o cyclonedx-json@1.6=<file>` writes 1.6 and `SYFT_CHECK_FOR_APP_UPDATE=false` sets
  `check-for-app-update` (H9): checked.
- `docker buildx imagetools inspect --raw` of a per-architecture tag returns the bytes of the
  `RepoDigests` digest (H19): checked locally.
- The runner's Docker writes a single-platform manifest to `RepoDigests` (H18): seen locally with
  the classic builder and the `overlay2` store; the runner is checked by the `sbom` job's guard and
