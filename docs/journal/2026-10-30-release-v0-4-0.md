# 2026-10-30 — Release v0.4.0

The release change for v0.4.0: the version, the changelog, and the docs that called the v0.4
features unreleased.

## Request

Prepare the release change for v0.4.0, as [Maintain the repository](../how-to/maintain.md) ("Cut a
release", step 1) describes, on top of the research notes that closed the measurements 0017 and
0019 set before release ([Richer context,
measured](../research/2026-10-29-richer-context-measured.md), [Standby and
failover](../research/2026-10-29-standby-and-failover.md)).

## What was done

- **The release change** (`chore(release): v0.4.0`): `version` 0.4.0 in `Cargo.toml` and
  `Cargo.lock` (only kausa's entry changed) and `version` and `appVersion` 0.4.0 in
  `charts/kausa/Chart.yaml`; the changelog's `Unreleased` entries moved to `[0.4.0] - 2026-10-30`,
  with a short summary, an empty `Unreleased` and the compare links updated. The summary names
  what the release adds (the detection rules `D011` to `D014`, `D014` from a new Deployment
  watch; the richer context of [0017. Send the model resource requests, probe handlers, image pull
  settings and an unschedulable Pod's scheduling keys, reduced and
  redacted](../adr/0017-richer-context-for-the-model.md); the optional standby replica of [0019.
  Offer an optional standby replica that takes over through a chart-created Lease, elected by
  kausa's own code](../adr/0019-high-availability.md)) and three upgrade notes taken from the
  `Changed` and `Fixed` entries: the image and the chart upgrade together (the new image needs the
  chart's `deployments` rule to become Ready), the fingerprints of `D001` and `D003` change once,
  and the default memory limit is `192Mi`.
- **The docs now say the features are in v0.4.0** instead of "in development", "not released" or
  "for v0.4": the README (the status, which now names the Deployment watch and the standby, and
  the roadmap, whose v0.4 entry gains the richer context and the measured takeover), the front
  page, the [Security policy](../../SECURITY.md) (supported versions and threat model),
  [Permissions](../reference/permissions.md), [Helm chart](../reference/helm-chart.md), [Command
  line and log format](../reference/command-line.md), [Install kausa with
  Helm](../how-to/install-with-helm.md) (whose standby section no longer says that its times are
  still to be measured), [Try kausa against a cluster with a local
  model](../how-to/try-with-a-local-model.md), [Architecture](../explanation/architecture.md) and
  the status comment of `src/run.rs`. Statements about what was run on 2026-10-29, and the
  statements about the v0.3 chart's role, stay as they were.
- **The install commands point at v0.4.0:** the README's quickstart installs `kausa-0.4.0.tgz`
  with `--set rbac.scope=cluster` and runs the crasher from `ghcr.io/fedeam/kausa:0.4.0`, and
  `CHART=` in [Install kausa with Helm](../how-to/install-with-helm.md) is the v0.4.0 chart. Both
  work only once the tag is pushed and the `Release` workflow has published them.
- `tests/chart/render.sh` needed no change: its comparisons name the tags `v0.1.0` and `v0.3.0`,
  not the chart's version, and the ones that would compare version labels are off by default.

## Decisions

- **0.4.0, not 0.3.1:** the release adds features, and an image upgraded without the chart (or
  with RBAC made outside it) is never Ready until it may list and watch Deployments, so it is a
  minor version, as Semantic Versioning asks before 1.0.
- No new ADR: the release follows [0012. Release from a tag: a signed image on GHCR and the chart
  on the GitHub release](../adr/0012-releases.md). No ADR was changed.

## Later the same day: a real Slack post

- The maintainer gave a test workspace's incoming webhook for one post. Its URL went to kausa
  through a file readable only by its owner, deleted right after; it was never printed, logged or
  committed.
- kausa v0.4.0 (a release build) watched a throwaway kind cluster with a crash-looping Deployment,
  used a fake model whose answer carried `@here`, `@channel`, `<!everyone>`, `<!channel>` and a URL,
  and posted one `slack` notification: `notification sent`, status `200`, attempt 1.
- What the maintainer saw: the URL was plain text, and the escaped `<!everyone>` and `<!channel>`
  showed as `!everyone` and `!channel`; but the plain `@here` and `@channel` were mentions that
  notified the channel. The documentation read on 2026-10-28 said that takes `link_names`.
- Fix, after v0.4.0: the Slack text gets a word joiner after every `@`, as the Telegram text does,
  added after the cut and counted by it. ADR 0015, the data reference, SECURITY.md, the how-to,
  the README and the front page say so.
- A second post, which the maintainer allowed, from a release build of the fix through the same
  webhook: status `200`, and the maintainer saw `@here`, `@channel` and `@everyone` as plain text,
  not as mentions, and the URL still plain text. The fuzz target of the notification bodies now
  checks the joiner after every `@` of the Slack text.
- An incoming webhook cannot delete what it posted: the maintainer deletes the message and, since
  its URL went through the chat, revokes the webhook.

## Later the same day: a hosted provider

- The maintainer gave API keys for one test each. Each went into a throwaway kind cluster as a
  Secret through standard input and was never printed or written to disk. The clusters were
  deleted, and the maintainer revokes the keys. The released v0.4.0 chart and image ran with one
  crash-looping Deployment, so each try was one incident.
- **OpenAI** (`https://api.openai.com/v1`, `gpt-4o-mini`): `429`, `insufficient_quota`, since the
  account had no credit. This still showed:
  - HTTPS from the distroless image works.
  - The key is accepted (no `401`).
  - The provider's error body is logged.
  - kausa retries once after 30 s, then skips the incident.
- **GitHub Models** (`https://models.github.ai/inference`): retired on 2026-07-30. The endpoint
  answers `200` with a plain-text `OK`, which kausa reports as `the answer is not JSON`. That is the
  right failure: the agent's suggestion to use it was wrong, not kausa.
- **Google's Gemini API** (`https://generativelanguage.googleapis.com/v1beta/openai`, its
  OpenAI-compatible endpoint, free tier):
  - `gemini-2.5-flash` answered `404`: it is no longer offered to new users.
  - `gemini-3.8-flash`'s first call hit kausa's 120-second timeout, and the retry got `503`, high
    demand.
  - `gemini-3.5-flash-lite` explained the incident: 546 tokens in, 131 out. The request's fixed
    fields (`temperature: 0`, `max_tokens`, and `response_format` with a strict `json_schema`)
    were accepted, and the `Explained` Event was written.
- This closes issue #9. No real cluster output went to any provider: the cluster held only the
  test Deployment.
