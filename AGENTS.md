# AGENTS.md — kausa

Instructions for coding agents and humans working in this repository; `CLAUDE.md` imports this
file. Start with [the documentation front page](docs/index.md), then the decisions in
[`docs/adr/`](docs/adr/).

These rules are the maintainer's repository standard, translated to English and made
self-contained because this is a public project. They hold for everyone; where a rule speaks of
approval, it means the approval of the person you are working for, and the maintainer's own
clone and remotes are described apart, under [Remotes, merges and CI](#remotes-merges-and-ci).

## What this repo is

kausa: a small Kubernetes controller in Rust (kube-rs), read-only except for its own Events, that
watches Warning events and
Pod status, groups the failures of one workload into one incident with deterministic rules, sends
a redacted context to one OpenAI-compatible model endpoint within a call and token budget, and
writes the explanation as a Kubernetes Event on the failing object. Open source,
`MIT OR Apache-2.0`. Pre-alpha: `kausa run` detects, groups and logs incidents, redacts their
context, explains them with a model within a call budget (or logs the request with `--dry-run`),
reuses explanations of repeated incidents, writes them as Events and serves metrics. The image and the Helm
chart are in the repository (not published); the kind test passes locally and waits for GitHub
Actions.
Maintainer: FedeAM (GitHub: `fedeam`).

## How to work

- **Context first:** read [the documentation front page](docs/index.md) and the ADRs before
  changing anything.
- **The simplest thing that works.** No feature, flag, rule or output format that is not backed
  by an accepted ADR. Do not refactor adjacent code you were not asked to touch.
- **English everywhere** that gets committed: code, comments, docs, commit messages, issues and
  pull requests. This is an exception to the maintainer's usual Spanish, recorded in
  [0004. Write everything in English](docs/adr/0004-english-only.md).
- **Honesty:** if you do not know, say so. Do not invent APIs, files, configuration, versions,
  SHAs, digests, checksums or license texts: fetch them from the official source and verify
  them. Mark anything you could not verify as a hypothesis.
- **Ask first** when something is ambiguous, and before destructive actions (`rm`, force push,
  deleting branches or tags).
- **Dependencies:** each new crate needs a reason in the pull request and must pass
  `cargo deny --locked check` (licenses, advisories, bans, sources). Prefer small, well-known
  crates; a crate that opens network connections or reads the environment needs an explicit
  reason.
- **What leaves the cluster and what kausa may read are decisions.** A new field in a request to
  the model, a new destination, a new permission or a weaker redaction rule needs an accepted ADR
  and, in the same change, an update to [Data sent to the
  provider](docs/reference/data-sent-to-the-provider.md),
  [Permissions](docs/reference/permissions.md) and the [Security policy](SECURITY.md).
- **Private agent notes** go in `.claude/notes.md` (gitignored), never in `docs/`.

## Commits

- [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) with a
  **required scope**: `type(scope): subject`. Types: `feat`, `fix`, `perf`, `refactor`, `style`,
  `test`, `docs`, `build`, `ci`, `chore`, `revert`, picked by user-visible effect (unsure: the
  smaller version bump).
- Subject in the imperative, lowercase start, no trailing period; header up to 72 characters.
  The body explains why. A breaking change takes `!` before the colon and a `BREAKING CHANGE:`
  footer.
- One logical change per commit. Reuse existing scopes (`git log --oneline`).
- **Pull requests are squash-merged on GitHub:** the pull request title, followed by GitHub's
  ` (#<number>)`, becomes the commit header on `main`, and the description its body, so both
  follow these rules. Keep the title to 64 characters, so that the header stays within 72. A
  change users will notice adds a line under `Unreleased` in [`CHANGELOG.md`](CHANGELOG.md).
- **No AI attribution** anywhere: no co-author trailer and no "generated by" footer naming an
  assistant.
- **Never** `--no-verify`; never skip hooks.
- **No commit and no push without explicit approval** from the person you are working for (in
  the maintainer's clone, the maintainer). Confirm the branch before the first commit of a
  session, and announce a new branch before creating it.

## How to build and run

```sh
cargo build --locked
cargo run --locked -- --help
# Watch the cluster of the kubeconfig's current context and log incidents (read-only):
cargo run --locked -- run
```

`rust-toolchain.toml` pins the compiler; rustup installs it the first time `cargo` runs in the
checkout. `kausa run` connects to the current context of the kubeconfig: before running it, check
`kubectl config current-context`, and never point it at a cluster you were not asked to use;
[Try kausa against a cluster with a local model](docs/how-to/try-with-a-local-model.md) shows a
read-only proxy that keeps it to its own reads. Tests never reach a cluster: `tests/cli.rs` runs
the binary with a nonexistent kubeconfig, and a new test that starts `kausa run` must do the same.
The core (`src/detect.rs`, `src/incident.rs`, `src/fingerprint.rs`, `src/owner.rs`,
`src/record.rs`, `src/redact.rs`, `src/context.rs`, `src/prompt.rs`) is pure and tested without a
cluster, and so are `src/budget.rs`, `src/metrics.rs` (except its listener) and the building of
Events in `src/events.rs`; `src/run.rs`, `src/explain.rs` and `src/events.rs` talk to the API
server and `src/model.rs` to the model endpoint.

## Verification (same as CI)

Run these before proposing a change; CI runs the same set, in the same order. If this list and
the CI workflow diverge, fix whichever is wrong in the same change.

```sh
gitleaks git --redact .
cargo fmt --all -- --check
cargo deny --locked check
cargo audit
helm lint --strict charts/kausa
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo test --locked --all-features
docker build --target ci .
```

The ci target also renders the chart with the value sets that change its templates (see the
Dockerfile). The image is `docker build --target runtime .`, and the end-to-end test in kind is
`tests/e2e/run.sh` ([Set up a development environment and run the
checks](docs/how-to/develop.md)); GitHub runs both.

The checks that run no code from the crate or its dependencies come first: clippy and the tests
compile and run build scripts, procedural macros and tests, which could tamper with whatever runs
after them. The CI image adds only output flags to `gitleaks`.

`docker build --target ci .` runs the checks inside the CI image, on Linux. GitHub's hosted
runners, which check pull requests, are linux/amd64; the Gitea Actions runner, which checks `main`
after each sync, is linux/arm64.

## Security rules

- **No secrets and no real cluster output** in any file, fixture, test corpus or commit message:
  no real logs, event messages, names or addresses, even sanitized by hand. Fixtures use obviously
  fake values: `example.com`, the documentation ranges `192.0.2.0/24` and `2001:db8::/32`, AWS
  account `123456789012`, and token strings that are visibly fake (a test for a token format uses
  a value built to match the format, never one that was ever issued).
- **No internal hostnames, private IP addresses, the maintainer's usernames on their own systems,
  the names of their clusters or personal data** in any file: the repository will be public. The
  only maintainer identity allowed is "FedeAM" and the GitHub handle `fedeam`.
- **Pin by digest or SHA:** container images by `@sha256:` digest, Actions by full commit SHA,
  crates through `Cargo.lock` and `--locked`. Take digests and SHAs from the registry or the forge
  API and verify them; never type them from memory.
- **kausa never reads Secrets or ConfigMaps, never writes anything but Events, sends nothing
  unredacted and nothing to any host but the API server and the configured endpoint, treats
  cluster text and model answers as untrusted, never acts on an answer, and bounds its cost and
  its resource use.** A change that weakens any of these is a security bug. Threat model:
  [Security policy](SECURITY.md).

## Remotes, merges and CI

Why it works this way: [0007. Take contributions and merge pull requests on
GitHub](docs/adr/0007-contributions-and-merges-on-github.md). The maintainer's commands:
[Maintain the repository](docs/how-to/maintain.md).

- **GitHub is where changes land.** Issues, pull requests, reviews and merges happen on
  [`fedeam/kausa`](https://github.com/fedeam/kausa). Pull requests are squash-merged there.
- **In a fork** (contributors): one remote is enough. Branch from your fork's `main`, push the
  branch to your fork and open a pull request against `fedeam/kausa`'s `main`
  ([Contributing to kausa](CONTRIBUTING.md)). The rest of this section describes the
  maintainer's clone; it does not apply to yours.
- **Nobody pushes new commits to `main`**, the maintainer included: every change, the maintainer's own too, is
  a pull request from a branch of `github/main`, pushed with `git push origin <branch>`. The only
  push to `main` is the sync, which carries commits GitHub already has.
- **Gitea is a private copy that runs the arm64 CI.** Its issues, pull requests and wiki are
  disabled. After each merge on GitHub, the maintainer syncs `main` to it. Agents do not merge
  pull requests or sync `main` unless the maintainer asks.
- **The maintainer's clone has two remotes.** `origin` fetches from Gitea and pushes to Gitea and
  GitHub (two push URLs, one `git push`). `github` fetches from GitHub; its push URL is disabled
  on purpose. **Never push to `github`** and never change the remotes: push through `origin`, and
  only with the maintainer's approval.
- **Start from GitHub's `main`.** Between a merge on GitHub and the sync, `github/main` is ahead
  of `origin/main`: run `git fetch github` and branch from `github/main`.
- **Never write the Gitea hostname** (or any internal URL) in a file, a badge or a commit.
- **CI:** the `CI` and `e2e` workflows on GitHub Actions check every pull request: the checks
  on linux/amd64, the image on both architectures, and the kind test. Gitea Actions
  (linux/arm64) checks `main` after each sync and once a week. Both run `docker build --target ci .`.
- **Dependency updates** come from Dependabot on GitHub (`.github/dependabot.yml`), which moves
  the `rust` image and `rust-toolchain.toml` together. The tools pinned by `ARG` in the
  `Dockerfile` are bumped by hand, as [Maintain the repository](docs/how-to/maintain.md)
  describes.

## README badges

Two lines under the H1.

- **The maintainer's standard**, first, in this order: `repository` (`private` or `public`),
  `internet` (`no`: kausa runs in its users' clusters and serves nothing on the internet) and
  `status` (`active`, `in development` or `archived`). Change a badge in the same change that
  makes it true: before the repository goes public, review the whole git history for secrets and
  internal names, commit `repository: public`, and only then change the visibility.
- **Project badges**, second. Static shields.io badges: `license: MIT OR Apache-2.0` and
  `rust: 1.99+` (the `rust-version` in `Cargo.toml`, the minimum supported Rust version), in
  `0969da`, the standard's blue, whose contrast with the white text is 5.19:1. The alt text
  repeats label and value; no logos. The CI, OpenSSF Scorecard, OpenSSF Best Practices,
  crates.io and docs.rs badges are added by [Publish the repository on
  GitHub](docs/how-to/publish-the-repository.md) once each one can work.

## Documentation

Diátaxis plus ADRs and a journal:

```
docs/
├── index.md       # front page (required): what it is, status with date, how to run it
├── tutorials/     # learning from zero
├── how-to/        # recipes and runbooks
├── reference/     # rules, permissions, data sent, configuration, tables
├── explanation/   # how it works and why: architecture, concepts
├── research/      # dated research before a decision: YYYY-MM-DD-slug.md
├── adr/           # decisions: NNNN-slug.md
└── journal/       # what a session did: YYYY-MM-DD-slug.md
```

- Folder names are fixed. A folder is created with its first page, never empty.
- One H1 per page; the first sentence after it summarises the page. File names in kebab-case.
- **ADR** (Michael Nygard's format): H1 `# NNNN. Decision in one sentence`, then
  `- Status:` (`proposed`, `accepted`, `rejected`, `obsolete` or
  `superseded by [NNNN](NNNN-slug.md)`) and `- Date: YYYY-MM-DD`; sections Context, Alternatives
  considered (optional, only alternatives that were really evaluated), Decision, Consequences.
  Numbers are never reused and ADRs are never deleted. Once accepted, only the Status changes, or
  an `Update YYYY-MM-DD: …` paragraph is appended; a new decision is a new ADR.
- **Journal:** `docs/journal/YYYY-MM-DD-slug.md`, H1 `# YYYY-MM-DD — Topic`. One per day, only
  when a session left relevant changes, decisions or incidents. Parts: the request in one line,
  what was done, decisions (linking the ADR), follow-ups. History, not state: never rewritten.
- Write for agents: absolute ISO dates, "Status as of YYYY-MM-DD" instead of "currently", exact
  names in `code`, acronyms defined on first use, unverified claims marked as hypotheses.
- Links are relative to the Markdown file, and the link text is the title of the target page.
